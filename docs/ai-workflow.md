# AI 工作流

这套东西只解决一个问题：**让 AI 的产出可验证**，而不是"聊得挺像那么回事"。

## 三层结构

| 层 | 载体 | 放什么 | 何时更新 |
|---|---|---|---|
| 项目记忆 | `AGENTS.md` | 事实：目录、构建命令、shader 管线、编码坑、禁区 | 项目结构或约定变了 |
| 流程 | `.dsh/skills/*/SKILL.md` | 做法：审查、改动、定位的固定步骤 | 流程本身需要改 |
| 验证 | 构建 + 日志 + 截图 | 证据：这次改动到底有没有用 | 每次改动 |

原则：**事实进 AGENTS.md，流程进 skill，证据留在日志和截图里。** 三者不要混——把事实写进 skill 会导致信息重复且容易过期，把流程写进 AGENTS.md 会让每次会话都带着一堆用不上的步骤。

## 三个 skill 的分工

| skill | 触发语 | 产物 | 权限 |
|---|---|---|---|
| `code-review` | 审查 / 检查 / 有没有 bug / review | 带证据的问题清单 | 只读 |
| `code-change` | 实现 / 修一下 / 改这段 | 最小改动 + 构建 + 验证记录 | 可写 |
| `renderer-debug` | 画面不对 / 崩了 / 没效果 | 根因 + 已排除的假设 | 可写（以实验为主） |

判断口诀：**想知道有没有问题 → review；想让它动手 → change；想知道为什么不对 → debug。**

## 典型串联

一次 LPV 的改动，正常走法是：

1. `code-review` 先看现状，拿到问题清单（或者确认没有明显问题）
2. `code-change` 按契约改一处，构建 + 跑通
3. 画面不对 → `renderer-debug` 定位
4. 修完后**再跑一次 `code-review`**，这次审的是自己的 diff
5. 提交（必要时 `git reset --soft` 压成一次）

第 4 步最容易被跳过，但它是把"能跑"变成"能交付"的那一步。

## 一次会话该给的信息

不要给"帮我看看代码"，给一个任务书：

```
范围：src/renderer/LPV/ 下 7 个文件（不含 shaders）
目标：找资源泄漏与 barrier 缺失，不找风格问题
验收：每条结论给出 文件:行 + 触发条件 + 为什么现有代码会失败
禁止：修改文件；不要动 VRPG2
```

少写一句的成本，通常等于多跑一轮对话的成本。

## 什么时候才需要多个 agent

- **要第二意见**：审查交给 `subagent`（干净上下文，看不到你的实现理由，不会顺着你的思路找借口）。
- **文件太多**：`workflow` 脚本按目录分区并行审，最后自己汇总。
- **不要**在单会话还不稳定时上并行 —— 那只是把噪音并行化。

多 agent 的真实成本在汇总：没有统一输出格式，5 个 agent 只会给你 5 倍噪音。

## 维护约定

- 项目结构或约定变了 → 改 `AGENTS.md`，不要改 skill。
- 某个流程反复出问题（比如审查总是报误报）→ 改对应 skill 的步骤或检查清单。
- skill 和文档**跟着仓库一起提交**，这样换机器、换会话都能复用。
