# 代码审查

目标：产出**可被证伪**的问题清单，而不是感受式的"看起来还行"。

## 铁律

- 本流程只读：不写文件、不跑格式化、不"顺手修一下"。需要验证时只给出建议命令。
- 没有范围就开始审查，必然漏。**先把范围变成文件清单**（≤15 个），超过就分批，每批单独交付。
- 每条结论必须有失败机理。说不出"什么输入或状态下会怎样错"的，写进"待确认"，不要当结论。

## 流程

### 1. 定范围

- 有明确目录或文件：直接用。
- "检查我的改动"：`git status --porcelain` + `git diff --stat`，只审改动文件及其直接调用方。
- "检查整个模块"：先列文件清单给用户确认，再逐批审。

### 2. 建上下文（决定审查质量）

- 读 `AGENTS.md` 里与该模块相关的段落（构建、shader 管线、编码坑）。
- 读模块自己的 `README.md`（如 `src/renderer/*/README.md`）。**没有设计意图，就无法判断"这是 bug 还是刻意为之"**。
- 找到入口与调用关系：谁创建它、谁调它的 update/draw、xml 参数从哪来。孤立读一个文件几乎必然误报。

### 3. 逐文件审

一次一个文件，读**完整文件**。只读 diff 容易漏掉上下文里的约定。按下面的清单过一遍。

### 4. 分级

| 级别 | 含义 |
|---|---|
| P0 | 会崩溃 / 结果明显错误 / 数据竞争 |
| P1 | 特定输入下错误 / 资源泄漏 / 未定义行为 |
| P2 | 健壮性：缺校验、错误处理缺失 |
| P3 | 可读性、风格 —— **默认不报**，除非用户问了 |

### 5. 输出

按置信度降序，默认 ≤10 条：

```
P1 | src/renderer/X/Foo.cpp:123
现象：当 <触发条件> 时，<具体错误>
机理：<为什么会错，引用关键代码事实>
修法：<最小改动>
置信度：高 / 中（不确定的写"待确认"）
```

最后补一行"本次未覆盖的范围"，避免用户误以为审完了。

## 检查清单（C++ / Vulkan / Slang）

- **生命周期**：Vulkan 对象销毁顺序；裸指针 vs shared_ptr；延迟删除队列；成员初始化顺序。
- **同步**：barrier / fence / semaphore 配对；descriptor 更新是否与 in-flight 帧重叠；GPU 写完 CPU 是否等过。
- **描述符**：set/binding 与 shader 声明一致；数组或 bindless 下标越界；更新时是否仍在录制。
- **布局**：C++ 与 Slang 结构体字段顺序、std430、vec3 对齐、数组 stride。
- **边界**：SSBO 容量、dispatch 组数、mip/层/实例数、除零、空 vector。
- **数值**：NaN 传播、pdf=0 时 MIS 权重、能量守恒、随机数范围。
- **资源**：early-return 路径上的泄漏；resize 重建时是否漏掉某个 buffer。

## 委派给子代理时

审查适合交给干净上下文的子代理（它不该看到你的实现理由）。brief 必须包含：

- 范围（文件清单，不是"整个项目"）
- 目标（找哪类问题：崩溃 / 数值 / 同步 / 泄漏）
- 证据要求（每条给 `文件:行` + 触发条件 + 机理）
- 输出格式与条数上限
- 禁止事项（只读、不改文件、不报风格）

拿回结果后**自己复核**：抽查 2~3 条回源码确认。子代理的结论同样需要证据。

## 不要做

- 不报"建议加注释 / 重命名 / 提取函数"（除非被问）。
- 不复述代码块。
- 不因为"看起来像 bug"就下结论 —— 先找触发条件。
